# Executed RMSNorm evidence

Generated by [probe-rmsnorm.py](../probe-rmsnorm.py), explained in [the case study](../rmsnorm-kernel-fusion.md).

- [summary.json](summary.json): pinned commit, environment, all eleven cases, buffer edges, counts, numerical checks.
- Each case directory: `schedule.json` plus tensor DAGs (`*.tensor.txt`), scheduled kernel ASTs (`*.ast.txt`) and actual generated CPU C (`*.c`).
- Counts exclude input setup and output host reads. All recorded schedules contain only compute calls.
- No compiled ELF binaries or timing results are committed. Dataflow buffer IDs are case-local; UOp node numbers are dump-local.

The artifacts are an observed CPU configuration, not expected golden kernel counts for every device or future commit.

## Read one result from the calculation to the emitted code

RMSNorm scales each row using the root mean square of its entries. With row width `N`, the denominator is `sqrt(sum(x[i]*x[i])/N + eps)`; each output then uses that denominator and its weight. The case study explains the complete computation and comparisons. These files answer a narrower question: what did the compiler represent and emit for each recorded case? The optional [first-principles guide](../../first-principles.md) explains graphs, kernels, and lowering.

Start with [rms_lazy/schedule.json](rms_lazy/schedule.json), then compare these representations:

| Artifact | Question it answers | How to read it |
| --- | --- | --- |
| [output.tensor.txt](rms_lazy/output.tensor.txt) | What computation was requested before scheduling? | A tensor **DAG** is a directed graph of dependencies without cycles. Each UOp is one operation; shared inputs can be referenced by several users. A tensor operation does not necessarily become a separate kernel. |
| [schedule.json](rms_lazy/schedule.json) | Which kernels and stored intermediates were selected? | A phase is one recorded scheduling step. Its kernel records list inputs and outputs; match their buffer IDs within this case to follow producer/consumer dependencies. **Materialization** means an intermediate becomes stored contents that later work can read. |
| [output.k0.ast.txt](rms_lazy/output.k0.ast.txt) | What work belongs to the first kernel before final code generation? | The AST label means an expression-structure dump; the numbered UOps can still share dependencies. `src=[...]` references earlier node numbers in this dump, `arg` holds operation-specific information, and dtype is the numeric type. |
| [output.k0.c](rms_lazy/output.k0.c) | How was that kernel implemented on this CPU path? | This is emitted C: explicit pointers, loops, loads, arithmetic, and stores. `k0` identifies the first recorded kernel, not the first tensor operation. Other `k` files show subsequent kernels. |

In the first kernel's AST, `PARAM` names a kernel input/output slot, `RANGE` represents iteration positions, `INDEX` selects a location, `REDUCE` combines values, and `STORE` writes a result. `SINK` collects the work retained as the kernel. The C makes those choices more concrete: the outer loop runs over four rows, the inner loop performs 32 groups of four float loads, and the accumulator adds the 128 squared values in each row. The constant `0.0078125` is `1/128`. The final square root produces one denominator per row. This reading describes the existing recorded artifact, not a newly run experiment.

`ast_ops` and `linear_ops` count graph operation nodes at different stages. They are not dynamic instruction counts: one operation inside a loop can execute many times. Likewise, scheduled storage may be an arena-backed byte buffer while generated C accesses a typed subregion. In this case the schedule lists `temp2` as 256 `char` elements, while the first kernel writes four floats. The allocation description alone is not the logical tensor shape; use the typed kernel interface and accesses to interpret its contents.

## Compare cases without overreading the evidence

Compare `rms_lazy` with `rms_staged` to see how explicit intermediate realization changes the schedule. Then use pairs such as `matmul_lazy` / `matmul_materialized` to inspect a consumer of RMSNorm. Follow buffer outputs into later inputs to understand the boundary between kernels; fewer arithmetic nodes within one kernel do not establish that a kernel boundary disappeared.

The `checks` records compare numerical outputs with the probe's reference. `max_abs_error` is the largest absolute element error; `rmse` is the root mean square error. `atol` and `rtol` are the absolute and relative tolerances used for comparison. Those checks provide numerical evidence for the recorded cases, while the schedules provide structural evidence. Neither reports speed: there are no timing results here. Consult the pinned environment in `summary.json` before comparing these files with a different device, setting, or source revision.
