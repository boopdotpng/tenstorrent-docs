Hardware tour · Tenstorrent

Inside Blackhole — a guided tour of every subsystem, using the emulator as our map.

Blackhole is Tenstorrent's standalone AI ASIC: a 2D torus of tiles, where each tile is a small computer in its own right. This post walks through every kind of tile on the chip — what it contains, how it talks to the others, and what role it plays — using the structure of the blackhole-py/emu cycle-structured emulator as scaffolding, because the emulator's source layout is a remarkably faithful diagram of the real silicon.

A reference / explainer · aimed at someone who has never opened a Blackhole datasheet but is comfortable with computer architecture.

01The big picture

A Blackhole ASIC is, internally, a grid of tiles — small, mostly-self-contained computers — wired together by two networks-on-chip. Every tile, regardless of its function, sits at a coordinate on that grid and speaks the same packet-based protocol. There are no global buses, no shared caches across tiles, and no special "host" core baked in: the host (when there is one) is just whatever sits behind a PCIe tile.

The full chip, before any harvesting, contains:

Tile kindCountWhy it exists
Tensix (worker / compute)140The AI workhorses. Where matmuls and elementwise ops actually happen.
DRAM (memory edge)2432 GiB of GDDR6, exposed in groups of three tiles per 4 GiB channel.
L2CPU (CPU cluster edge)4Sixteen SiFive x280 RV64 cores total — capable of running Linux on-chip.
Ethernet (network edge)14Up to 12 connected at 400 GbE each — chip-to-chip fabric, not just I/O.
PCIe (host edge)2PCIe 5.0 x16. Usually one connected to a host, one idle.
ARC & Security (management)2Power, thermal, boot, and root-of-trust. Customer code never runs here.

Product SKUs harvest some of those — the p150 board, for example, ships with 140 Tensix and 24 DRAM tiles enabled, but only 12 of the 14 Ethernet tiles and 1 of the 2 PCIe tiles routed to physical pins. Harvested tiles still exist as silicon; they just aren't usable.

Stylised floorplan. The real chip is a 2D torus (left/right and top/bottom edges wrap). Exact coordinates are documented in tt-isa-documentation/BlackholeA0/Diagrams.
Tensix DRAM L2CPU Ethernet PCIe ARC / Security empty (router only)
Why a torus? Every tile is at most ~half the grid dimension away from any other tile (in hops), so worst-case NoC latency is bounded and predictable. The torus also lets traffic flow uniformly without "edges" piling up at the corners.

02The NoC — how every tile talks

There are two NoCs on Blackhole. Both connect the exact same set of tiles and form a 2D torus. They are physically separate, and they flow in opposite directions: NoC #0 routes one way around the torus, NoC #1 the other. Software can pick either (or both, e.g. one for reads, one for writes) to relieve congestion and avoid deadlock.

Packets, flits, and NIUs

  • Every transaction is one or more packets; every packet is one header flit + up to 256 data flits.
  • Every flit is exactly 512 bits (64 B). So a single flit carries one cache-line-sized blob of data.
  • Each tile hosts a NIU (NoC Interface Unit) per NoC — that's the gateway between the tile's address space and the NoC fabric.
  • Routers, sitting between NIUs at every grid coordinate, handle the actual hop-by-hop movement.

Transaction kinds

TypePurposeNotable variants
ReadPull a contiguous span from receiver's address space back to (usually) the initiator's L1.—
WritePush initiator data (or a 32-bit immediate) into receiver's address space.posted, broadcast (to a rectangle of Tensix tiles), inline 32-bit, dual-target first 128 b, "notify overlay" flag
AtomicRMW against a 128-bit slot in receiver L1; 32-bit response back.increment, increment-and-get, 16-bit CAS, indexed store, 4-byte swap, posted variants

On Tensix and Ethernet tiles, the NIU's data path is wired straight into the tile's address space — so a NoC read is functionally a read from another tile's L1 (or registers) and arrives in your L1. The NIU's control path shows up as MMIO registers in the local tile, so the local RISC-V cores can post and poll NoC commands. Each tile also has a NoC Overlay: a small coprocessor that handles common patterns (like circular-buffer pointer updates, semaphore signalling on packet arrival, multicast fan-out) without burning a RISC-V to manage them.

A read on Blackhole: just NIU → router → router → NIU. The "request packet" goes one way; the "response packet" comes back the same way (NIUs sit on both NoCs).
Software responsibility. NoC hardware guarantees deadlock freedom for most ordinary traffic, but a few advanced features (multi-packet transactions, broadcasts without path reservation, mismatched virtual-channel use) push that guarantee onto you. Tooling like tt-metalium generally hides this from app authors.

03Tensix tile — the worker

Each Tensix tile is the chip's atomic unit of compute. Despite the name "tile," a single Tensix is itself a multi-core little computer. Inside, you get:

L1 SRAM1536 KiBPlain RAM (not a cache). Locally addressable, NoC-addressable from any other tile.
5× "Baby" RISC-V cores5Small RV32 cores: BRISC, NCRISC, and three TRISCs.
NoC connections2NIU0 + NIU1, one per NoC.
NoC Overlay1Coprocessor that helps drive NoC transactions without RISC-V intervention.
Tensix coprocessor1The big AI engine — see below. Not a RISC-V; it has its own ISA.
Utilities—Mailboxes, TDMA-RISC, debug timestamper, PIC.

The labour split

The 5 baby RISC-Vs are not where work gets done — they're conductors. The expected division of labour is:

  • 2 RISC-Vs drive the NoCs (one per NoC) — typically BRISC and NCRISC. They issue reads/writes, watch flags, and stage data in/out of L1.
  • 3 RISC-Vs drive the Tensix coprocessor — TRISC0, TRISC1, TRISC2. They emit Tensix instructions to keep the unpackers, math units, and packers fed.

A baby RISC-V on its own is anemic — that's by design. Performance comes from the Tensix coprocessor next door, and from the NoC overlay handling hot-path streaming. The RISC-V is just the choreographer.

All on-tile traffic transits L1. The five RISC-Vs don't compute — they keep the NoC and the Tensix coprocessor busy.

04The Tensix coprocessor — where math actually happens

This is the most distinctively Tenstorrent part of the chip. It's a wide pipeline organised around tiles of data (typically 32×32 elements) that flow from L1, into "DST" accumulator registers, and back out to L1. Three engines and a thread controller share the pipeline, and four kinds of mover shuffle data on the boundaries.

Unpacker (×2)

Streams operand tiles out of L1, applies any required format conversion (BFP8 → BF16, padding, etc.), and lands them in the engine's source registers. Two unpackers in parallel, so an FPU op can have both operands in flight at once.

Matrix unit / FPU

The matmul engine. Low-precision multiply-accumulate (think BFP8/BF16/FP16 in, FP32 accumulate) over 32×32 tiles. Also handles a few non-matmul matrix operations (transpose, broadcast variants). This is what gives Blackhole its peak TFLOPs.

Vector unit / SFPU

32-wide SIMD over 32-bit lanes. FP32 multiply-accumulate, transcendentals, comparisons, lookup-table activations, integer ops. This is where things like GELU, softmax tails, and quantisation pre/post-process actually run.

Scalar unit / ThCon

Integer scalar ops, plus 128-bit memory operations against L1 — including the L1 atomics other tiles can target over the NoC. Sometimes called the "thread controller." Cheap glue logic for the TRISCs.

Packer (×4)

Pulls results out of the DST accumulator file, format-converts (e.g. FP32 → BFP8), and writes back to L1. Four packers means a single math op can fan out into multiple outputs in parallel.

DST register file

The accumulator scratchpad: a small bank of FP32 (or FP16/BF16) tiles where matmul results live before being packed. Half-/full-DST sync modes pick how aggressively the packers and the FPU can overlap.

How a "kernel" actually executes

A typical Tensix kernel is three parallel TRISC programs, all reading from a small cfg-register layout and a few shared mailboxes: 

TRISC0 (unpack)   loop:  unpack_tile_a()   unpack_tile_b()   signal(MATH)
TRISC1 (math)     loop:  wait(UNPACK)      matmul()          signal(PACK)
TRISC2 (pack)     loop:  wait(MATH)        pack_tile()       signal(WRITER)
BRISC/NCRISC      loop:  noc_async_read()  noc_async_write() handle CB ptrs

Synchronisation is done via small hardware mailboxes (the sync module in the emulator) and via L1 semaphores that NoC atomics target. The circular buffer (CB) abstraction in tt-metal layers cleanly on top: producers reserve pages, consumers wait for pages, the NoC overlay can poke pointers when remote writes land.

Mental model. A Tensix tile is a tiny dataflow machine bolted onto a NoC port. Five RV32s compose a stream from L1, through the Tensix engines, back to L1, and then off to another tile. There is no cache hierarchy hiding anything — every byte motion is software-visible.

05DRAM tile — the GDDR6 edge

There are 24 DRAM tiles on a full Blackhole, exposing 32 GiB of GDDR6. The trick is that the same 4 GiB chunk of GDDR6 is exposed by three DRAM tiles in parallel — so each 4 GiB region has 3 entry points on the NoC. That lets compute consume bandwidth from three sides at once, which is how Blackhole reaches usable memory bandwidth without a single monolithic memory controller bottleneck.

Inside a DRAM tile:

  • The NIU's data path is wired straight to the GDDR6 channel — a NoC read on this tile's address space is, mechanically, a GDDR6 read.
  • One small "baby" RISC-V core + a small piece of L1, used for management, init, and bookkeeping (not for customer compute).
  • Two NIUs (one per NoC), as everywhere else.

Harvested products (e.g. p100) disable some DRAM tiles, leaving 21 of 24 active and 28 of 32 GiB usable.

06L2CPU tile — the on-chip Linux box

This is the most surprising tile to a newcomer: Blackhole has a real CPU complex on-die. Four L2CPU tiles, each one a coherent cluster of four SiFive x280 RV64 cores. That's 16 application-class CPUs sharing the same NoC as everything else.

x280 cores per L2CPU tile4
L2CPU tiles per chip4
L1-D cache (per core)32 KiB
L1-I cache (per core)32 KiB
L2 cache (per core)128 KiB
L3 cache (per cluster)2 MiB
NoC TLB windows (per tile)256

Each cluster has a direct connection to one neighbouring DRAM tile (CPUs 0-3 to D5; 4-7 to D6; 8-15 share D7), which means it sees a fixed slice of GDDR6 in its address space without going over the NoC. For everywhere else — other DRAM tiles, Tensix L1, even host memory through PCIe — the L2CPU provides 256 TLB windows mapping NoC regions into the x280's virtual address space. So the x280s can mmap any tile in the chip, run Linux, and treat the whole NoC as memory.

Watch out: due to a hardware bug in A0, once an x280 hart leaves reset, you can't put it back into reset without resetting the whole ASIC (tt-smi -r). Software typically uses RNMIs to "park" harts instead.

The tt-bh-linux repo in this tree is the in-tree Linux that boots on those cores. It's a normal-ish RISC-V kernel that happens to live inside an AI accelerator.

07Ethernet tile — the chip-to-chip fabric

Blackhole's Ethernet tiles are not just I/O — they are a primary scale-out mechanism. Each Ethernet tile drives one 400 GbE link, with the full MAC / PCS / PHY on-die. A pair of tiles ganged together feeds one QSFP-DD port, giving 800 GbE per port. The p150 board exposes 4 ports (8 connected tiles), with 4 more Ethernet tiles present but not wired to a connector.

Inside an Ethernet tile:

  • 512 KiB of L1 SRAM (smaller than a Tensix's, but same flavour: plain RAM on the NoC).
  • 2 baby RISC-V cores — yes, both run customer code; the second one is new in Blackhole.
  • 2 NIUs + 1 NoC overlay, exactly like a Tensix.
  • 1× 400 GbE link, surfaced as 3 TX queues + 3 RX queues with substantial header insertion/removal logic in front of them.

This makes Ethernet tiles look, from a programmer's point of view, very much like a "Tensix tile that has 400 GbE instead of a Tensix coprocessor." The tt-metal fabric layer (and projects like tt-metal-lite-fabric) treats them exactly that way, weaving multi-chip dataflow programs across NoCs of multiple Blackholes as if it were one bigger NoC.

08PCIe tile — the host bridge

Two PCIe 5.0 x16 tiles. Both are physically present on every Blackhole; only one is connected at a time on shipping boards. The PCIe tile is where customer code typically arrives: the host driver writes a kernel image into a Tensix's L1 over PCIe, then writes a launch-message that the RISC-V cores polling on it pick up.

The conversion stack

The PCIe tile is a two-way protocol gateway:

DirectionStack
Host → devicePCIe TLP  →  AXI  →  NoC packet
Device → hostNoC packet  →  one-or-more AXI  →  one-or-more PCIe TLPs (split for max-payload + 4 K boundaries)

A NoC request larger than 128 B will likely become multiple PCIe TLPs on the wire; that's a normal thing to budget for when sizing transfers. The device-to-host address space was extended to 64 bits in Blackhole (it was 32 in Wormhole), and there's a fresh 32 GiB region in BAR4 on the host side — both make zero-copy host-side IO substantially nicer.

Trivia: only PCIe 1 has a direct wire to the ARC tile. So if your boot sequence is going through PCIe 0 (as on p150), reaching ARC from the host actually goes through the NoC. That's transparent in software, but it shows up if you're staring at an ILA trace.

09ARC & Security tiles

Two small management tiles round out the chip. They don't run customer kernels.

ARC tile

Houses the chip's management processor (an ARC core, hence the name). It owns power and thermal management, clock/voltage trim, telemetry, and the boot state machine. Tools like tt-smi and luwen talk to it. The Zephyr-based firmware that runs here lives under tt-zephyr-platforms.

Security tile

Root-of-trust + secure boot anchor. Holds keys, performs early image verification, and gates the rest of the chip from coming up if the chain of trust fails. Customers typically don't interact with it directly.

10The emulator — and why its layout mirrors the chip

That brings us to blackhole-py/emu. It's a cycle-structured emulator: not a perfect-cycle-accurate model of every transistor, but a model where work is decomposed into the same units as the silicon and advanced through the same kinds of phases. That makes its source tree a useful map of the chip:

Emulator file / packageWhat it models
device.pyThe whole Blackhole ASIC — instantiates all tiles at their NoC coordinates and wires them up.
noc.pyThe two NoCs: routers, NIUs, request/response packets, atomics, virtual channels, deadlock-aware paths.
memory.pyAddress spaces and L1 banks (Tensix L1, DRAM L1, GDDR6 channels).
rv.pyRV32 / RV64 baby-RISC-V (and x280-shaped) execution, with the Blackhole instruction extensions.
tensix_core.pyThe Tensix coprocessor as an aggregate — wraps the units below into one issue/commit pipeline.
tensix/unpack.pyThe two unpackers and their format conversions.
tensix/math.pyMatrix unit (FPU) + vector unit (SFPU) functional + timing models.
tensix/thcon.pyScalar unit / thread controller (ThCon) — incl. the L1 atomic engine.
tensix/pack.pyThe four packers + DST → L1 paths.
tensix/mover.pyThe dedicated L1↔engine movers (the "TDMA"-flavoured paths).
tensix/sync.pyMailboxes & semaphores between the three TRISCs.
tensix/tdma.pyTDMA-RISC: the small DMA helper exposed to the baby cores.
tensix/cfg_layout.pyThe Tensix configuration register file (the "knobs" that select formats, tile shapes, sync modes, ...).

timing.pyThe cycle-phase scheduler.

The four phases per cycle

The emulator advances through four ordered phases each cycle, as documented in emu/README.md:

The phase split prevents same-cycle observation bugs that pure functional models accidentally allow.

The crucial property: instructions don't directly mutate architectural state when decoded. They issue operations into units, which reserve resources in a scoreboard and schedule a completion cycle. Real silicon couldn't possibly let one component peek at another's same-cycle write — and Python loop order would quietly let it, if the model were a single big step(). The phase split forces the model to honour the same visibility rules as the chip.

Why this matters for understanding the chip

The emulator is a second source of truth alongside the ISA documentation. When a question like "can a packer commit while the math unit is mid-flight?" or "does an unpacker's L1 read get reordered around an NoC write to the same address?" comes up, the answer is encoded both in the spec and in the way the units' commit and issue phases are wired together in the emulator. They should agree; if they don't, that's a bug in one of them.

The same shape applies to the bigger picture. device.py instantiates each tile kind from this post — Tensix, DRAM, L2CPU, Ethernet, PCIe, ARC, Security — and connects their NIUs through the noc.py torus. If you can read the constructor of device.py, you can read the chip.
